## 1. Email OTP via Resend

- Send with plain HTTPS `POST https://api.resend.com/emails` and a Bearer API key. No SDK needed (Go stdlib `net/http`); this adds zero dependencies. Source: [Send email](https://resend.com/docs/api-reference/emails/send-email.md).
- Idempotency: header `Idempotency-Key`, 1 to 256 characters, valid 24 hours, same key with a different payload is rejected (400 `invalid_idempotency_key` for bad length). Use the outbox message key (002 already resends with the same key after a crash). Sources: [Idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys), [Engineering idempotency keys](https://resend.com/blog/engineering-idempotency-keys).
- Domain `mail.swastikapp.co.in` is already verified (`docs/engineering/handover.md`). Use a from-address on it, for example `no-reply@mail.swastikapp.co.in`.
- Free plan: 3,000 emails per month and 100 per day, counting sent and received. Fine for about 100 clients (a sign-up needs 1 to 3 emails). Sources: [Sending limits](https://resend.com/docs/knowledge-base/resend-sending-limits), [Pricing](https://resend.com/pricing.md). The 100/day cap is shared with 013/014 reminder fallback emails, so the planner should budget it.
- Rate limit is per team and a strict one-second window; 429 carries `retry-after`. **VERIFY** default: sources say 2, 5 and 10 requests per second. Treat it as 2 per second worst case; the relay's batch size already serialises sends. Sources: [Rate limit](https://resend.com/docs/api-reference/rate-limit), [API intro](https://www.resend.com/docs/api-reference/introduction).
- Recommendation: a small `internal/otp` (or `internal/auth`) Resend `outbox.Sender` over `net/http` with a 10 s timeout; map 429 and 5xx to retry, other 4xx to permanent failure. Never log the recipient or body.
- Rejected: Brevo (300/day free but needs a second vendor account and sender setup; the domain is already verified on Resend). Rejected: Resend Go SDK (`resend-go`), a new dependency for one POST call.

## 2. Mobile verification via Firebase Phone Auth

- Flow (ADR 0004): the client runs Firebase phone sign-in, gets an ID token, sends it to our API; the API verifies it and marks the mobile verified. Firebase never becomes the session system; discard its session after verifying.
- Android and iPhone native: `@react-native-firebase/auth` with the Expo config plugin; on SDK 58 the plugin patches SceneDelegate for reCAPTCHA redirects. Needs a dev build, not Expo Go. Source: [RNFirebase phone auth](https://rnfirebase.io/auth/phone-auth). Per CLAUDE.md run `npx expo install` for it in `apps/client` (that is feature 024's work).
- iPhone PWA (web): Firebase JS SDK `signInWithPhoneNumber` with an invisible `RecaptchaVerifier`. Source: [Web phone auth](https://firebase.google.com/docs/auth/web/phone-auth.md.txt). **VERIFY on a real iPhone PWA**: no source covered standalone-PWA behaviour (storage partitioning, reCAPTCHA iframe). Make this a spike before 024 depends on it. The sign-in is used only to prove the number, so `linkWithPhoneNumber` is not needed.
- Server verification in Go, recommendation: plain JWKS/JWT verification, not `firebase.google.com/go/v4`. firebase-admin-go pulls in the large Google Cloud SDK tree for one function. Rules from [Verify ID tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens): `alg` RS256, `kid` present in Google's keys, `iss` = `https://securetoken.google.com/<projectId>`, `aud` = project id (`swastik-4fcc9`), `sub` non-empty, `exp` in future, `iat`/`auth_time` in the past; refresh keys by the response `Cache-Control: max-age`. Keys: x509 endpoint `https://www.googleapis.com/robot/v1/metadata/x509/securetoken@system.gserviceaccount.com` (official) or the JWKS twin `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com` (same RS256 keys, used by [PowerSync](https://docs.powersync.com/configuration/auth/firebase-auth)). Use the JWKS URL.
- Reuse: `go-oidc/v3` (approved in 002) already powers `internal/platform/tickauth` (`NewOIDC`, `WithJWKSURL`, `WithHTTPClient`) and `go-jose/v4` (approved in 003). Build a `firebaseauth` verifier the same way (go-oidc `RemoteKeySet` caches and rotates keys), no new module. Mirror the P-19/depguard confinement.
- After verifying, require `firebase.sign_in_provider == "phone"` and read `phone_number` (E.164, **VERIFY** claim names against a real token in a test fixture). Compare it with `auth.NormalizeMobile` of the pending user's number; mismatch = reject. Require `auth_time` within the last 5 minutes so an old token cannot be replayed; keep a single-use record (store a hash of the token `jti`-like key `sub`+`auth_time`) so one token verifies once.
- Rejected: `firebase-admin-go` (heavy dependency, needs service-account credentials we otherwise do not need on the API). Rejected: Identity Platform "check revoked" calls (needs credentials, adds latency, no benefit for a one-shot proof).

## 3. India SMS, cost, abuse

- Cost: Phone auth needs the Blaze plan (already set up). First 10 SMS per day are free, India listed at about $0.07 per SMS beyond that. **VERIFY** on the live page. Sources: [Identity Platform pricing](https://cloud.google.com/identity-platform/pricing), [Firebase pricing](https://firebase.google.com/pricing). At about 100 clients, SMS stays near zero; set a Google Cloud budget alert and an SMS daily quota in the console as a cap.
- DLT: no source says Firebase requires the app owner to register on DLT; Firebase sends the SMS from its own senders and templates, so the owner does not register headers/templates. **VERIFY** with a real Indian test (delivery to Jio, Airtel, Vi; Google Groups report [delivery problems on Indian carriers](https://groups.google.com/g/firebase-talk/c/8SU6FSS1wOk)). If delivery proves unreliable, the fallback is a DLT-registered Indian SMS provider (MSG91, Fast2SMS) behind the same outbox Sender, a later owner decision (new vendor).
- Abuse controls: Firebase does its own checks (Play Integrity then reCAPTCHA fallback on Android; silent push then reCAPTCHA on iOS; reCAPTCHA on web). Source: [Android phone auth](https://firebase.google.com/docs/auth/android/phone-auth), [iOS phone auth](https://firebase.google.com/docs/auth/ios/phone-auth.md.txt). Recommend: turn on an **SMS region policy allowing only IN** (handover says India-only is set), keep reCAPTCHA enforcement on, and defer App Check enforcement. Known conflict: App Check with the reCAPTCHA Enterprise provider can break web SMS auth ([firebase-js-sdk#7060](https://github.com/firebase/firebase-js-sdk/issues/7060)); Play Integrity needs a Play Store build ([RNFirebase App Check](https://rnfirebase.io/app-check/usage)). Our own limits (section 5) also protect SMS cost because the API only lets a registration reach the Firebase step after email is verified and the account is pending.
- Test numbers: use Firebase fictional test numbers in staging and CI so no real SMS is sent.

## 4. Email OTP design (best practice)

- Code: 6 digits from `crypto/rand` (uniform, `rand.Int`), never `math/rand`. TTL 10 minutes. Single use: invalidated on success and on issuing a newer code. Sources: [OWASP MFA cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html) (short TTL, single use, attempt limits, no plaintext at rest, no logging).
- Attempts: 5 wrong guesses per code, then the code is dead and a resend is needed; 6 digits has 10^6 values so 5 tries is a 1-in-200,000 guess. OWASP testing guide range is 5 to 10 ([lockout](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/03-Testing_for_Weak_Lock_Out_Mechanism)). These numbers are policy, owner-confirmable in the spec.
- At rest: store only a keyed digest. A plain SHA-256 of 10^6 codes is brute-forceable from a DB dump, so use HMAC-SHA-256 with a server key and bind it to (purpose, contact, code id). Reuse `platform/crypto` (`Digest`, `BlindIndexer` HMAC) rather than writing new primitives. Compare with `subtle.ConstantTimeCompare` (or `hmac.Equal`) on digests.
- Resend cooldown 60 s per contact; max 5 sends per contact per hour and per day, plus a per-IP limit (section 5). Same response shape whether or not the account exists (OWASP [forgot password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html): uniform message and timing). Never put the code in the outbox row in plain text beyond what is required to render the email (see section 5).
- Purposes: `register_email` (BR-CLI-04), `change_email` and `change_mobile` to the NEW contact (BR-CLI-05, feature 007 reuses this); the old contact gets a notice (outbox message, no code).

## 5. Fit with 002 and 003

- Outbox (`internal/outbox`): `Message`, `Envelope`, `Recipient`, `Sender` interface; the relay sends after commit, with quiet hours, backoff (`platform/retry`) and per-recipient order. The OTP service writes the code row and the outbox message in one transaction; the relay calls the Resend `Sender`. **Open for the plan**: OTP email must not wait for quiet hours (IST night). Check whether `Options`/`istdate.QuietHours` has a bypass for transactional kinds; if not, a small outbox change is needed (spec question, not a guess).
- The email body needs the plain code, so it lives in the outbox payload (`db.MaxPayloadBytes` 8192, `MarshalPayload`) until sent. Options: (a) payload holds the code, the relay purges it on `sent_at` and 002 retention clears the rest; (b) payload holds only the OTP id and the Sender regenerates nothing (impossible, hashed). Recommend (a) with a short expiry (`expires_at` = code TTL, 002 expiry never sends a stale code) and a rule that outbox payloads are never logged. Planner to confirm 002's retention and withdraw-by-key (new code withdraws the old message).
- Throttles: `platform/ratelimit.Limiter` (in-memory, keyed, `New(limit, window, maxKeys, now)`) for per-IP and per-contact bursts; `auth.Throttle`/`ThrottlePolicy`/`ApplyThrottle` (DB-backed, per-key state, used for lockout) for durable per-contact and per-code attempt counting. Use the DB one for send and verify limits (Cloud Run instances scale, so memory-only limits are bypassable); `ClientIP` in `platform/httpx` for the IP key.
- Audit: `platform/audit.Write` with 003's pattern (`Action*`, `Entity*`, `Reason*` consts, per-event `*After` structs). No raw contact or code in audit (ADR 0007 point 3, FR-091). Contacts are stored readable (ADR 0007), so lookups need no decryption.
- Status: `auth.StatusPendingVerification` already exists; 004 flips email/mobile verified flags only; approval is 005.
- Jobs: expired code rows purged by a scheduler job, like `auth.housekeeping` (`scheduler.JobRegistrar`).

## 8. Pitfalls

- Resend free daily cap (100) is shared across all senders; a flood of resend requests can exhaust it for everyone. Hence the per-contact and per-IP limits, and the outbox's attempt budget.
- Firebase tokens last 1 hour but must be accepted only fresh (`auth_time`); clock skew: allow 30 s leeway, injectable clock (`platform/clock`).
- Firebase SMS to Indian numbers can be delayed; the UI needs a resend timer and Firebase's own resend limits apply on top of ours. Firebase throttles by IP and phone and returns `too-many-requests`; surface a calm message (copy via `packages/domain` error codes).
- App Check and reCAPTCHA settings are console state (not in code); record the chosen settings in the runbook.
- Do not log contacts, codes, or ID tokens (ADR 0007, constitution VI).
